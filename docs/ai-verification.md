# Методика верификации решений, полученных с использованием ИИ

Сквозная методическая линия дисциплины (актуализация РПД 2026): технологии искусственного интеллекта допускаются как **вспомогательный инструмент**, но любое решение — своё или сгенерированное — до включения в отчёт проходит верификацию по настоящей методике. На защите обучающийся объясняет и решение, и результаты его верификации.

## 1. Четыре шага верификации

### Шаг 1. Инварианты

Для реализуемой структуры данных или алгоритма формулируются и проверяются (assert-ами или проверочной функцией) ключевые инварианты. Примеры:

| Объект | Инварианты |
| --- | --- |
| Сортировка | выход упорядочен; выход — перестановка входа (мультимножества совпадают); для стабильной сортировки — сохранение порядка равных ключей |
| Динамический массив | размер ≤ ёмкость; элементы доступны по индексам 0..size-1 |
| Стек / дек | LIFO/FIFO-порядок; push/pop согласованы по количеству |
| BST | для каждого узла: ключи слева < ключа узла < ключей справа; in-order обход даёт отсортированную последовательность |
| Хеш-таблица | каждый ключ находится в цепочке своего бакета; количество элементов равно сумме длин цепочек |
| Поиск подстроки | каждое возвращённое вхождение действительно совпадает с шаблоном; ни одно вхождение не пропущено (сверка с наивным поиском) |

### Шаг 2. Репрезентативные тесты

Проверка на наборах, покрывающих классы входов, а не только «средний случай»:

- **граничные**: пустой вход, один элемент, два элемента;
- **вырожденные**: все элементы равны, уже отсортированный вход, обратно отсортированный;
- **типовые**: случайные данные нескольких размеров (seed по варианту);
- **специфичные для задачи**: отрицательные числа и дубликаты для сортировок; отсутствующий ключ для поиска; коллизии для хеш-таблицы; перекрывающиеся вхождения для поиска подстрок.

### Шаг 3. Сравнение с эталонной реализацией

Результат сверяется с доверенным эталоном на сотнях случайных входов (property-based-подход «на коленке»): `sorted()` для сортировок, `str.find` в цикле для подстрок, `dict` для хеш-таблицы, линейный скан для поиска ближайших соседей. Любое расхождение — дефект, который надо локализовать и объяснить.

### Шаг 4. Оценка сложности и производительности

- **Аналитически**: вывести асимптотику решения (худший/средний случай, память) и сравнить с ожидаемой для задачи.
- **Эмпирически**: замерить время на ряде размеров входа по методике бенчмаркинга ([`reproducibility.md`](reproducibility.md)) и сверить наблюдаемый рост с заявленной асимптотикой. Классическая ловушка ИИ-кода — корректная, но асимптотически худшая реализация (например, O(n²) там, где ожидается O(n log n)): её выявляет только этот шаг.

## 2. Вывод о применимости

По итогам шагов 1–4 формулируется обоснованный вывод: **принять / принять с доработкой / отклонить**. Вывод входит в отчёт по работе и оценивается критерием «обоснованность выводов» рубрики.

## 3. Правила использования генеративного ИИ в дисциплине

- **Разрешено**: пояснение материала, отладка, генерация тестовых данных, черновики реализаций — с обязательной верификацией по шагам 1–4.
- **Обязательно**: итоговый код должен быть понятен обучающемуся; на защите он воспроизводит и объясняет решение и отвечает на вопросы КИМ.
- **Запрещено**: сдача сгенерированного решения без верификации и понимания — приравнивается к невыполнению работы (0 баллов по критерию «понимание на защите» и «полнота верификации»).
- На зачёте использование внешних источников и ИИ запрещено, кроме явно разрешённых преподавателем справочных материалов.

Примеры промптов для корректной работы с БЯМ (пояснение, генерация тестов, ревью собственного кода) — в [`resources/llm-prompts/`](../resources/llm-prompts/README.md).

## 4. Связь с оценкой

Критерий «полнота верификации» присутствует в рубрике каждой ЛР и ДЗ с весом 0,20 (см. [`methodical-guidelines/teachers-assessment/`](../methodical-guidelines/teachers-assessment/README.md)).
